## Method (Pass A / Pass B, verdicts, §6)

- **Pass A — zero-code baseline:** against a bare conversation log + Gemini API, what breaks if the unit is deleted, and can the model supply it via log, prompt, or response schema? If the model can supply it, DELETE.
- **Pass B — strict ZFC:** the model owns all campaign-domain facts; the server provides ONLY transport, durable writes, tool execution, authorization, and bounded capacity. A field-aware transform fails unless it names a specific registered exception AND proves that exception necessary. Registry membership alone proves nothing; determinism, schema validity, display formatting, or normalization alone never justify a field-aware transform.
- Verdicts are exactly KEEP / ADAPT / DELETE. ADAPT names the change. Final verdict = stricter of the two passes, unless a named product promise rescues it (named explicitly where used).
- Reference counting first: zero callers = DELETE unless entry point, test target, or proven registered exception. Symbols (constants, tables, enums) get the same passes. Each symbol row below carries 2–4 sentences covering both passes and ends in its verdict.
- **Jeffrey's standing decisions (§6, override everything else):** (1) server logging KEEP; where it blocks a player turn, ADAPT to async/batched delivery. (2) Anti-cheat KEEP; dice resolution stays ON the turn path; only the audit trail may go async. (3) Faction/living-world KEEP but ADAPT to async background ticks merged on the next turn.
- **Minimal-auth-set judgement:** the minimal set is ONE auth path, not three. Applied here: Firebase user auth (outside this group) remains the one user sign-in path. Apple SIWA is NOT a sign-in path — it is account-deletion token revocation required by Apple App Store Guideline 5.1.1(v), a named product promise, so it does not count as a second/third sign-in path and is kept in kind. The OpenRouter PKCE/KMS cluster is NOT a user sign-in path either — it is BYOK credential custody (server authorization + secret custody) for a user-supplied provider key; that is why its core is kept in kind rather than deleted as a duplicate login, while its duplicated delegation wrappers are deleted and its ceremony is flagged for slimming. **Conflict flagged explicitly:** the OpenRouter cluster still maintains a second *identity* system (subject hashes, uid-owner records, link completions) parallel to Firebase identity; that duplication is real and is the reason the wrapper/duplicate rows below are DELETE and the cluster's module verdict is ADAPT (collapse onto Firebase uid + one custody record), even though the custody core itself is KEEP.
- **Provider-abstraction judgement:** the abstraction is needed in kind (it is what makes a model switch cheap). Provider-specific cruft for dropped providers deletes — which is why MiniMax (no production dispatch) is DELETE in full, while Gemini/OpenRouter/Cerebras (all dispatched from `llm_service.py`) keep their transport cores.
- **§6 conflicts flagged explicitly:** (a) faction patching in `provider_utils` currently runs on the synchronous response path — conflicts with §6(3); verdict ADAPT to async ticks, not DELETE. (b) BigQuery/telemetry serialization in `gemini_provider` is exhaustive and field-aware — it is rescued in kind by §6(1) logging KEEP, but only in slimmed, async/batched form; the exhaustive spec/alias tables themselves are DELETE. (c) No verdict below deletes server logging, moves dice off the turn path, or deletes faction work outright; where a dice-adjacent helper is ADAPT, the dice leg is explicitly kept on-path.
