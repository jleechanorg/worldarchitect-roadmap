## Governing decisions (§6, override everything else)

1. Server logging KEEP; where it blocks a player turn, ADAPT to async/batched delivery.
2. Anti-cheat KEEP — server dice/mechanics integrity stays; dice resolution itself stays
   ON the turn path (narration cannot depend on a roll that has not happened); only the
   audit trail around it may go async. The need is ONE RNG + ONE audit trail, not a dice
   cluster — every additional dice routine must earn its place individually.
3. Faction/living-world KEEP but ADAPT to async background ticks — no file in this set
   touches faction state except `dice.py:execute_unified_tool`, which only routes to
   faction tools and does not mutate faction state itself.

## Method (in order, per unit)

Pass A — zero-code baseline: against a bare conversation log + Gemini API, what breaks if
the unit is deleted, and can the model supply it via log, prompt, or response schema?
If the model can supply it, DELETE. Pass B — strict ZFC: the model owns all
campaign-domain facts; the server provides ONLY transport, durable writes, tool
execution, authorization, and bounded capacity. A field-aware transform fails unless it
names a specific registered exception AND proves that exception necessary. Registry
membership alone proves nothing; determinism, schema validity, display formatting, or
normalization alone never justify a field-aware transform. Verdicts are exactly
KEEP / ADAPT / DELETE. ADAPT names the change. Final verdict is the stricter of the two
passes, unless a named product promise rescues it (named explicitly per row where it
applies: anti-cheat server dice, server logging, persistence across sessions,
multi-user separation, bounded cost).

## Explicit conflicts flagged (first-pass instinct vs §6 — §6 wins)

1. Strict-ZFC instinct would DELETE server success/total derivation (`dice.py`
   `_natural_outcome_for_d20`, `dice_code_execution_audit`
   `maybe_apply_natural_outcome_to_code_execution_event`, `dice_integrity`
   `_apply_tool_results_to_structured_response` overriding model rolls, and the Social HP
   projections) as second-guessing model outcomes. §6 anti-cheat rescues them, but ONLY
   on the narrow ground actually present in the code: every one of these operates on
   server-verified evidence (server-tool RNG results or RNG-verified sandbox stdout),
   never on model narrative claims, and the model still owns the DC, the target, and the
   attribution. If any of them ever ran on unverified model JSON, its verdict would flip
   to DELETE.
2. `derived_stats.py` claims "ZFC-exempt structural data" plus a registry spec
   (`conclude.reconcile_derived_stats`). That exemption claim is REJECTED under this
   spec — registry membership proves nothing. Its rescue is different and narrower: the
   module performs no transform at all (see its table); its only production consumer is
   a warn-only invariant that never mutates state, which falls under server logging
   (§6.1), not under an exemption.
3. One-RNG need vs two RNG surfaces: the live path seeds Mersenne Twister with a
   stamped seed, while `dice_rng.seeded_rng_int` is a second, SHA-based sampler used by
   no production turn path. The sampler and its canary move out of the game path
   (ADAPT); the duplicate canary in `dice_provably_fair` is DELETE.
4. `dice_integrity._check_god_mode_narrative` polices narrative with verb/pronoun
   substring lists. That is keyword routing, which the repo's own house rules ban, and
   it is not authorization in any meaningful sense. ADAPT to a mode/schema check.
5. `dice_integrity.safe_resolve_dice_audit_events` returns the raw, unverified model
   events when resolution throws. That fail-open fallback contradicts the anti-cheat
   promise it exists to serve. ADAPT to fail-closed.

## Phase 1 — file verdicts

- **dice.py — KEEP.** Pass A: deleting it removes the only server-side roll execution
  (native two-phase tools) and the code-execution audit dispatch, so every roll would
  be a model claim and the anti-cheat promise would be gone; the model cannot supply
  trustworthy randomness through the log or schema. Pass B: it is tool execution plus
  bounded capacity (notation caps), rescued explicitly by the anti-cheat server-dice
  promise; its two contained ADAPT items (async logging, single natural-outcome pass)
  do not change the file's disposition. Verdict: KEEP.
- **dice_integrity.py — ADAPT.** Pass A: deleting it removes fabrication detection and
  the server-tool override, so fabricated model rolls would persist and display as
  real; the model cannot be its own auditor. Pass B: the fabrication/audit core is
  authorization plus audit-trail transport and is rescued by anti-cheat, but the file
  as shipped also carries turn-blocking telemetry, a fail-open resolver fallback, and a
  keyword-based narrative check, each of which must change as named in Phase 2.
  Verdict: ADAPT.
- **dice_rng.py — ADAPT.** Pass A: deleting the whole file would lose seed stamping,
  which the live provably-fair path depends on, and the model cannot stamp a seed it
  must not know before the roll. Pass B: stamping is part of the one RNG and stays,
  but the SHA sampler and chi² canary are not on any production turn path and must
  move out of the game path into an offline canary/test helper. Verdict: ADAPT.
- **dice_provably_fair.py — ADAPT.** Pass A: deleting it loses the pre-roll commitment
  and seed injection/verification, so players could no longer verify any roll and the
  model could pick its seed after seeing the outcome. Pass B: commitment, generation,
  injection, and extraction are the anti-cheat core, but the file also carries three
  re-export shims, a weaker substring seed check, and a duplicate canary that must go
  as named in Phase 2. Verdict: ADAPT.
- **dice_code_execution_audit.py — KEEP.** Pass A: deleting it removes the only reader
  of verified sandbox stdout, so code-execution rolls would have no audit trail and
  fabricated stdout claims could not be distinguished from real ones. Pass B: it reads
  and arithmetically normalizes server-verified execution output (transport plus audit
  trail), and its outcome derivation is rescued by anti-cheat because its inputs are
  RNG-verified faces, not model prose. Verdict: KEEP.
- **dice_strategy.py — KEEP.** Pass A: deleting it forces every provider down one dice
  channel, breaking providers whose runtime cannot execute code (AGY CLI, Cerebras,
  OpenRouter) or forcing code execution where it is unsupported. Pass B: it is pure
  transport routing on model/provider capability, deciding no campaign fact and
  touching no campaign state. Verdict: KEEP.
- **action_resolution_utils.py — ADAPT.** Pass A: deleting it breaks the shared
  action-resolution plumbing (accessors, notation bounds used by the face check,
  response assembly) that the live path reads every turn. Pass B: most of it is
  transport and audit arithmetic, but two public extractors have zero production
  readers and the roll normalizer mutates persisted rolls in place, both fixed as
  named in Phase 2. Verdict: ADAPT.
- **derived_stats.py — KEEP (conditional).** Pass A: deleting it removes only a
  warn-only consistency oracle; no player-visible capability breaks, because the model
  already authors the canonical stats and the module never writes state. Pass B: it
  performs no field-aware transform (it returns mismatch names; its sole production
  caller logs a warning and never mutates), so it survives as server logging/telemetry
  under §6.1 — on the explicit condition that it stays warn-only; any caller that
  gates, clamps, or overwrites on its output flips this file to DELETE. Verdict: KEEP.
- **class_lookup.py — KEEP.** Pass A: deleting it removes SRD corpus retrieval for
  level-up prompts, so the model would have to recall class tables from weights alone
  and custom/homebrew handling would collapse into guessing. Pass B: it is retrieval
  of static reference data keyed on typed fields (system, class, level), assembled
  into prompt context — the server supplying reference text, not adjudicating
  campaign facts. Verdict: KEEP.
- **progression_outcome.py — ADAPT.** Pass A: deleting it loses only the
  post-persistence progression telemetry event; no roll, level, or XP value changes,
  because the event is emitted after the write it describes. Pass B: the event
  contract and receipt predicates are durable-write bookkeeping, rescued as server
  logging/telemetry under §6.1, but emission must move to async/batched delivery so
  telemetry never sits on the turn response path. Verdict: ADAPT.
