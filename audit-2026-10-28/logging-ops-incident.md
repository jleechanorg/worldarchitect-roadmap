## Method

- **Pass A (zero-code baseline):** against a bare conversation log + Gemini API, what breaks if the unit is deleted, and can the model supply it via log, prompt, or response schema? If the model can supply it, DELETE.
- **Pass B (strict ZFC):** the model owns all campaign-domain facts; the server provides ONLY transport, durable writes, tool execution, authorization, and bounded capacity. A field-aware transform fails unless it names a specific registered exception AND proves that exception necessary. Registry membership alone proves nothing; determinism, schema validity, display formatting, or normalization alone never justify a field-aware transform.
- **Final verdict** = stricter of the two passes, unless a named product promise rescues it (named explicitly). Verdicts are exactly KEEP / ADAPT / DELETE.
- **Reference counting first:** zero production callers = DELETE unless entry point, test target, or proven registered exception. Each row below is 2–4 sentences covering both passes and ends in its verdict. Module-level constants are grouped per file section with every symbol named; each grouped row's verdict applies to all symbols it names.

## §6 standing decisions — application and conflicts flagged

1. **Server logging KEEP, never blocking a turn.** This governs the whole group. Every logging unit below carries an explicit blocking/async determination: on-path-and-blocking → ADAPT to async/batched delivery; already async → KEEP. No logging unit is DELETE on zero-code grounds, because §6-1 overrides Pass A for logging itself; the ADAPT is the stricter Pass B outcome (delivery mechanism, not existence).
2. **Anti-cheat KEEP; dice resolution stays on the turn path; only the audit trail may go async.** Applied to `log_dice_roll` only — see the flagged conflict there.
3. **Faction/living-world KEEP but async** — not in this group's scope; no verdict here depends on it.

**Conflict flagged (§6-2 vs. reference counting, `bq_logging.log_dice_roll`):** §6-2 preserves a dice audit trail in principle, but `log_dice_roll` has **zero production callers** (verified by grep over the whole tree; its only caller is `tests/test_bq_logging.py`). Verdict is DELETE, with re-introduction (async-only) trivial if a caller is ever wired. The parent should confirm before any deletion, since the test would also need updating.
**No other §6 conflict found.** In particular, the §3 first-pass instinct (incident cluster = ops tooling, DELETE-candidate; debug files = do not ship) is **not sustained** against actual callers: the incident journal/observer/registry/adapters are wired into the player stream path (`main.py`, `llm_parser.py`, `llm_service.py`, `firestore_service.py`, `bq_logging.py`), and `debug_hybrid_system.py` is wired into player-visible story display (`world_logic.py`, `llm_response.py`). Blocking determination for the whole file: the background-telemetry machinery (`submit_background_telemetry`, the two executors, drop counting) is already async and is the §6-1-compliant delivery path. ADAPT for those four means: default them to `background=True` (or route their callers through `submit_background_telemetry`), returning the disk-mirror/queued status instead of a live insert id where a caller currently consumes one (`llm_capture.py` consumes `log_llm_payload`'s insert id — that caller must be slimmed to not require it, or the function must return a locally generated id immediately and insert async). Schema/migration/auth helpers are KEEP: they are transport provisioning, invoked from the background warmup or from the (to-be-async) entry points, and deleting them would break the durable sink §6-1 keeps.
